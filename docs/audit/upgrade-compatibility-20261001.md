# 原型1.0から1.2.0への載せ替え互換性調査

調査日：2026-10-01。対象：`west-japan-family` にある原型1.0と、開発版1.2.0（`30b7ce1`）。原型の参照リポジトリは `d45414b4`。

## 結論

**修正後の隔離試験では、手動でファイルを交換するだけで、既存設定・未変更の旧PHPテンプレートによる入力→確認→送信→完了が成立した。新方式への切り替えは、更新方法と関係なく管理画面から明示的に行う。**

初回調査で再現した未登録入力値の欠落・返信先空欄の失敗、旧添付形式・REST応答の差異を修正した。下記の初回調査は履歴として残す。実SMTP・外部サービス・公開Releaseによる更新は今回の合格範囲に含めない。

調査対象は、**同じ既存サイトの設定・テーマを変更せず、プラグインのみ交換した場合**。fam-securityとwest-japan-familyの項目数・項目名・デザインの違いは問題として扱っていない。サイトごとに項目が違うこと自体は正常。

原型サイトは読み取り専用。載せ替え互換性を維持する修正は利用者の承認に基づく。原型サイトにあるOMF以外の更新差分には触れていない。

## 修正後の確認（2026-10-01）

`tests/integration/upgrade.py` は、架空の宛先・本文・独立したDBを使い、原型と同じ設定・未変更テンプレートで確認する。原型の有効化後、新版へファイルだけを交換し、再有効化・設定保存・更新イベントによる移行は行わない。

| 確認対象 | 修正・結果 |
| --- | --- |
| 旧入力・hidden・連想添字の選択値（U-01） | コード方式で保持。管理画面方式は定義済み項目のみ。ネスト・単一宛先への配列・偽の添付辞書は拒否 |
| 任意の返信先が空欄（U-02） | コード方式は返信を省略し、通知成功で完了。非空欄の不正宛先や配送失敗は成功扱いにしない |
| 添付形式・更新前セッション（U-03） | `attachment_id`・画像情報・メールタグを維持。実体は非公開へ移し、本人・管理者のみ取得可能。移行失敗時は再添付を求め、欠落したまま送信しない |
| 添付の保管・削除 | 旧方式の送信済みメディアを保持。未送信の期限切れ実体・メディア情報と、管理者が削除した実体を削除。偽造ID・パストラバーサル・実行形式を拒否 |
| REST v0（U-04） | 原型のHTTP 200とJSONを維持。認証NGは実際にはHTTP 200内の `error_data.failed.status:404`。有効なnonce／トークンによる送信と、使用済みトークン拒否を確認 |
| 動作条件（U-05） | PHP 8.0へ対応。WordPress 6.3／PHP 8.0.30で載せ替え81項目、PHP 8.0で構文80ファイル・回帰9スクリプトが成功 |
| 原型の更新メニュー（U-06） | 権限・nonce検証とWordPress展開処理で維持。GitHubの展開名を正規化し、設定と有効状態を保持。ローカルZIPを使用し、公開masterの取得は未実施 |
| Google認証（U-07） | 旧暗号の読み出し・移行を維持。移行後に原型へ戻す場合のDBバックアップが必要という制限は残る |
| 外部通信（U-08） | 旧HTTPヘルパー・並列HTTP・Google認証の既定60秒を復元。TLS検証は有効のまま。実サービスの疎通は未実施 |
| 履歴抑止・送信後フック（U-09・U-10） | 旧完了スクリプトをコード方式に復元。同期直列の失敗時も旧フックへ入力値を渡し、完了・トークン消費とは区別する |
| CAPTCHA（U-11） | 更新後の通過・失敗・確認から送信を模擬応答で確認。信頼できる通過記録がない更新前相当の確認は、送信せず入力で再認証を求める |
| CSV（U-12） | 旧コード方式は先頭ゼロの値を維持。数式注入対策は維持。管理画面方式の先頭ゼロ保護は継続 |
| 方式切り替え | 管理画面で新方式を保存し、新APIへテーマを調整した後に送信・完了まで確認。管理画面で旧方式へ戻し、原型テンプレートで再度送信可能 |

最新版のHTTP結合214項目（配送34・cron HTTP10・ページ連携10・FSE権限6を含む）、PHP回帰9スクリプトが成功。WordPress 7.1.2／PHP 8.3.33と、WordPress 6.3／PHP 8.0.30の載せ替え試験はいずれも81項目成功。新版による警告・例外の追加なし。メールは捕捉し、外部APIは試験用の固定応答に限定した。

WordPress 6.3の試験はヘッダーの最低値に合わせて開発側が追加した補足確認であり、利用者の今回の対象要件ではない。追加の利用者試験やリリース前の必須確認にはしない。

その後の利用者指示により、最低対応WordPressを **6.9.9以上** に変更した。6.3での成功記録は要件変更前の履歴であり、対応対象ではない。公式の[6.9.9リリース情報](https://wordpress.org/documentation/wordpress-version/version-6-9-9/)でもセキュリティ修正を確認した。対象環境7.1.2は新要件を満たす。

### 更新時の注意と未確認

- 通常の旧方式継続に追加設定は不要。新方式に切り替えるときだけ、項目の用意・保存とテンプレート調整を行う。旧HTMLから項目を自動抽出する機能ではない。
- セキュリティ例外：公開添付URL、危険なファイル形式、偽造した添付情報、自動返信への実体添付、未認証送信は復活させない。CAPTCHA付きの更新前確認画面は再認証が必要な場合がある。認証なしの旧挙動を維持しない方針は修正前に利用者へ報告した。
- 旧添付の非公開保存先は自動選択・保存する。既存の一時添付の場所を優先し、新規ではWordPressの隣の非公開領域を優先する。最後にサーバーの一時領域を使用する。非公開領域に書き込めない環境では添付を安全に停止する。保存先はバックアップ対象とし、一時領域を使う場合はサーバーの自動消去に注意する。
- 実SMTPの同期直列・並列は利用者確認済み。ただし今回の互換性試験は実配送を遮断している。WP非同期の実受信、実サーバーの定期cron、CAPTCHA・Slack・Sheetsの実アカウント、公開ReleaseのZIP更新、全ホスティング環境は未確認。
- 戻す場合は更新前のプラグイン・DB・添付のバックアップを使用する。Google認証情報の移行や旧一時添付の非公開化後に、プラグインのファイルだけを原型へ戻す方法は保証しない。

## 初回の載せ替え試験（修正前の履歴）

独立した一時WordPress（7.1.2／PHP 8.3.33）に原型を導入し、既存形式の設定・ページ連携・未変更の原型PHPテンプレートを設置。その後、再有効化をせずプラグインディレクトリのみ新版へ交換した。

- 元サイトから参照した設定は検証条件のみ。メール宛先・本文は架空のものを使用し、実アカウントの認証情報・問い合わせ記録はコピーしていない。
- `wp_mail` は捕捉して成功を返し、WordPressの外部HTTP通信を遮断した。実SMTP・Google・Slackへの疎通試験ではない。
- 原型がHTTPでもSecure Cookieを発行するため、試験クライアントのみループバック接続でそのCookieを返すよう調整した。製品のCookie設定は変更していない。HTTPS・実ブラウザーの履歴操作はこの試験の対象外。
- 試験用DB・サイト・サーバープロセスは終了後に削除した。

31確認中25一致・6不一致。不一致6件の内訳は、入力値欠落の3確認、返信先空欄の1確認、RESTの1確認、旧版への戻しの1確認。独立した6不具合という意味ではない。

| 確認対象 | 結果 |
| --- | --- |
| 未変更の入力・確認・完了テンプレート | 更新前後で動作。新版用APIへの書き換え不要 |
| 確認テンプレートが入力値のhiddenを再出力しない方式 | 更新前後で送信可能 |
| 自動返信・通知の2通生成 | 通常の宛先ありケースで更新前後とも成功 |
| フォームの保存済みメタ | 交換前後のハッシュが一致 |
| フォームの作成方式 | 未設定の既存フォームはコード方式を維持 |
| 送信方式 | 未設定の既存フォームは同期・直列を維持 |
| 原型の受付記録 | 投稿タイプ・件数を保持 |
| 更新前に開いた確認画面からの送信 | 添付・CAPTCHAなしの試験では継続可能 |
| 未登録入力値の確認表示・メール・送信後フック | 原型は保持、新版は欠落（U-01） |
| 返信先が任意で空欄の送信 | 原型は完了、新版は失敗扱い（U-02） |
| RESTのバリデーションNG | 原型200、新版400（U-04） |
| 原型の暗号化済み認証情報の復号 | 初回保存・2回目以降の両形式で新版が復号・移行可能 |
| 移行後の認証情報を原型で復号 | 不可。戻すときは更新前バックアップが必要（U-07） |
| 全テキスト項目に入っている旧file_size設定 | 新版がテキストを添付と誤認しない |

## 初回調査で確認した影響（修正前の履歴）

### U-01：バリデーション未登録の入力値が消える【高・再現済み】

原型はPOSTの入力値を取り込み、制御用キーを除いて保持していた。新版の `restrict_array_values()` はバリデーション設定の `target` にあるキーだけを採用する。

旧コード方式では、検証不要の任意項目や独自hiddenをテンプレートに置き、バリデーション設定へ登録しない使い方ができた。そのまま載せ替えると値が確認画面・メール・保存／連携用データから失われる。検証設定が空なら、設定に依存する取り込み結果も空になる。

実際に、同一テンプレート・同一設定・同一POSTを使った更新前後比較で、設定のtargetにない通常の文字列が、確認表示・メール本文・既存の `omf_after_send_mail` 引数から欠落した。項目名がサイト間で違うことが原因ではない。

根拠：新版 [入力値の取り込み](../../classes/class-page.php)、[設定済みキーだけを採用する処理](../../classes/class-trait-validation.php)。原型 `class-page.php::get_post_values()` は全POSTの取り込み後に制御キーを除外する。

対応案：コード方式では旧来の通常入力値を維持する経路を設ける。ファイル情報の偽装防止や不正配列の検証は維持し、ビルダーの項目定義を旧コード方式の受付制限として流用しない。

### U-02：返信先が空欄だと完了できなくなる【高・再現済み】

原型の通常ページ送信では、返信先が空なら `send_reply_mail()` が `no-reply` を返し、通知メールが成功すれば完了する。新版は空の宛先を `false` とし、同期直列の成功判定が返信と通知の両方の成功を要求する。

メールアドレスを任意にした既存フォームで再現。新版では通知を生成していても送信失敗扱いになり、完了に進めない。自動返信そのものをOFFにした場合とは別のケース。

根拠：原型 `class-trait-send.php::send_reply_mail()` と `class-page.php::send_mails()`。新版 [自動返信処理](../../classes/class-trait-send.php) と [同期直列の成功判定](../../classes/class-trait-submission.php)。

対応案：旧コード方式の「返信先なし＝返信省略」を維持する。通知の実送信失敗まで成功扱いにする変更は不要。

### U-03：添付ファイルの受け付け方・データ形式が変わる【高・コード比較で確認】

原型は `$_FILES` をメディアへ保存し、入力値へ `attachment_id`・`image` 等を追加する。メール処理では `id`・`name`・`url`・`src` 等の配列へ変換する。新版は非公開保管の `upload_id` を使用し、メール向けタグではファイル名へ変換する。

- `attachment_id`・画像プレビュー・公開URLを参照する既存テンプレート／フックは、そのままの形式では利用できない。
- 原型は拡張子設定がなくてもアップロードを処理する。新版は明示的なfile型か、空でない `extension` 配列がある項目だけを添付として扱う。旧設定がサイズ上限のみの添付は、載せ替え後に受け付けられない可能性がある。
- 更新前の添付セッションは、新版の `*_uploaded_files` と `upload_id` の保管形式へ移行されない。更新中の訪問者が再添付を求められる可能性がある。
- 公開領域外の書き込み可能な一時保存先が必要。サーバーの一時ディレクトリが公開領域内しか使えない場合は、従来より環境要件が増える。

根拠：新版 [添付項目の判定](../../classes/class-trait-validation.php)、[添付の保存・タグ変換](../../classes/class-trait-send.php)、[セッション復元](../../classes/class-trait-submission.php)、[非公開保存先](../../classes/class-uploads.php)。

今回の載せ替えHTTP試験には添付を含めていない。原型の添付フォームを用いたHTTP比較は未実施。公開URLを復活させる対応は避け、必要な旧表示・フック契約をどう維持するか先に決める。

### U-04：既存RESTクライアントのエラー処理が変わる【中・一部再現済み】

`omf-api/v0/validate`・`send` のURLは維持されるが、バリデーションNGは200から400、送信失敗は200から502、認証失敗は404から403へ変更されている。検証NGの200→400は、同じ設定・nonce・リクエストで再現した。

旧クライアントが「HTTP成功時にJSONの `valid:false` を読む」構成なら、更新後は項目エラーを表示する処理へ到達しない可能性がある。通常のPHPフォームPOSTにはこのHTTP契約変更は影響しない。

根拠：[REST応答・権限処理](../../classes/class-rest.php)。対応案：既存v0の契約を維持するか、別のAPI版として提供する。既存クライアントの修正を必須にするなら、載せ替え互換とは扱えない。

## 維持されている契約

- `Sharesl\Original\MailForm\OMF` の名前空間と、既存テンプレート用の `get_post_values()`・`get_errors()`・`nonce_field()`・`recaptcha_field()`・`turnstile_field()`・`get_omf_token()` は残っている。
- フォーム投稿タイプ `original_mail_forms`、保存データの `omf_db_<フォームID>`、ページ連携の `cf_omf_select`、旧設定メタキーを維持する。既存のメール文面を読み取り時に新しい標準文面へ置換しない。
- 原型のフォーム連携ONを引き継ぐ。既存フォームをビルダー・ショートコード・非同期へ自動移行しない。新しいテーマ用APIの採用も必須ではない。
- 原型にあるアクション／フィルター名は残っている。ただし呼び出すタイミングやデータ形式はU-03・U-10の影響を受ける。
- 受付記録の保存期限は、未設定では自動削除しない。
- 原型の主要ファサードAPIに削除はない。一方、独自コードが内部クラスを直接呼ぶ場合、削除された更新メソッドや必須引数の増えた `OMF_Admin::add_meta_box_posts()` 等の影響は別途確認が必要。

## 初回調査で挙げた対応（履歴）

1. U-01・U-02を、旧コード方式の動作を維持する修正対象として扱う。
2. 添付とRESTの契約を、旧版互換として維持する範囲を決める。仕様変更にする部分は更新案内へ明記する。
3. 初回更新方法・最低動作環境・認証情報を含む戻し方を整える。
4. 修正後に同じ載せ替え試験を行い、添付・任意メール・既存RESTクライアントを追加して確認する。

現段階では原型からの互換性確認を完了扱いにしない。実SMTP・外部連携・公開ZIPによる更新・古いWordPress/PHP環境は未確認であり、今回の試験結果から成功とは判断できない。
